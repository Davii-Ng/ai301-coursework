# Rubric: is this plan ready to post and build from?

Every check reads the plan package against the reproduction evidence
and the thread, never against the write-up's length, headings, or
confidence. A terse plan can pass every check; a long, polished one can
fail. Worked pass/fail examples for each check live in
`references/evidence-guide.md` under the family named in the check.

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| diagnosis-grounded | The plan's stated cause (the sentence(s) that say what is wrong and where) read against every run in the repro-evidence block: the failing run, each control run, and any debug/trace step. Also the thread highlights, when the plan adopts a cause from the thread. Evidence guide: "Diagnosis and grounding". | Passes when the plan states a cause, that cause explains the failing run, AND it is consistent with every control in the repro evidence: for each control, the outcome the cause predicts is the outcome the control shows. The proposed change acts on that cause, not only on its symptom. A cause that is consistent but not yet proven passes (an honestly named unknown is fine). Fails if: any control or trace step contradicts the cause (a control shows the blamed component working, or shows the failure happening before/without the blamed code running); the plan names no cause at all, or only restates the symptom ("the export is slow"); the plan adopts a cause from the thread that the package's own evidence rules out (thread confidence never outranks a control); or the only change is a workaround, documentation, or a catch-all suppression (blanket recover/try-catch) while the evidence localizes a code defect. | required |
| bounded-scope | Every change the plan proposes (numbered steps, "proposed changes", prose "Change:" lines), plus its not-in-scope / out / deferred statement, read against the single behavior the issue and repro pin down. Evidence guide: "Scope". | Passes when the plan is one bounded change: every proposed item is either the fix for the reproduced behavior, the same fix applied at sibling sites of the same defect in the same code path, or a test for it; AND the plan states its limits in any wording (what it will not touch, or what it defers). Deferring the bigger rework, filing an adjacent symptom as its own issue, or "list other suspect sites for reviewers without fixing them" all pass. Fails if any item goes beyond the reproduced behavior: a refactor or module restructure, a redesign/state-machine/abstraction layer, a new option, setting, prop, or UI, a dependency upgrade or library migration, new CI jobs or matrices, fixing other symptoms "while in the area", or open-ended "maybe also check other X". A correct core fix bundled with any of these still fails. Also fails if the plan states no limit at all. | required |
| stranger-executable | The plan's files/functions/areas and its approach steps, plus every decision the plan leaves open. Evidence guide: "Executability". | Passes when someone new to the issue could start the change after one read without asking the author anything: the plan names where the change goes (file, module, or function; a named area plus a stated way to pin the exact function is enough) AND names the concrete change it will make there (the approach is chosen, not to be discovered). A bounded, named unknown (which of two named functions holds the check; exact line to confirm with a log already in hand) passes. Fails if the plan's steps are investigation verbs with no chosen change ("investigate", "profile", "figure out", "look into", "optimize whatever turns up"), names no file or area, or defers a real decision to build time ("somewhere", "in our fork or upstream, whichever is easier", "library A or library B? not sure"). | required |
| test-decisive | The plan's test plan read against the repro evidence's failing step and its expected/actual lines. Evidence guide: "Test plan". | Passes when at least one test re-runs the reproduced trigger (the repro's command/steps, or an automated test encoding that exact case) AND states the expected observable result after the fix: an output, exit code, value, rendered state, or the named symptom being absent on that specific run ("prints `1.01`, exit 0", "the saved file opens and lists 3 rows", "no leftover temp-file handle across 20 runs"). Fails if the only tests are generic ("run the full test suite", "CI passes", "nothing regresses"), the expected result is a feeling or adjective ("should be snappier", "works correctly", "behaves better", "no other regressions"), or no test touches the reproduced case. | required |
| comment-faithful | The candidate plan comment, sentence by sentence, read against the candidate plan and the repro evidence. Evidence guide: "Honesty". | Passes when every commitment and claim in the comment is held by the plan or the evidence. The comment may summarize and leave details out. Fails if the comment: promises a change, test, or result the plan does not contain; describes the scope as smaller or different than the plan ("one contained change" over a multi-area plan, "docs only" over a code plan); states as certain what the plan marks unknown, or claims a cause/verification the evidence does not show; or commits to a fixed deadline or guaranteed outcome ("by Friday", "this week", "guaranteed fix"). Soft intent ("will send the PR shortly", "will report back once tests pass") passes. | required |
| thread-and-policy | The plan comment (and plan) read against (a) maintainer-side statements in the thread highlights: comments by OWNER, MEMBER, or COLLABORATOR, or a CONTRIBUTOR who opened the issue or is giving the design direction; and (b) the `contribution policy` line in the repo-facts block. Evidence guide: "Comms". | Two parts, both must hold. (a) Thread: if a maintainer-side comment names a culprit or fix site, settles or rejects an approach, or posts a patch/test build, the plan or comment engages it: follows it, builds on it, or names it and says why it diverges. Ignoring such direction fails, including a plan that swaps in a different remedy (e.g., a docs workaround) without mentioning the maintainer's located culprit or patch. No maintainer direction in the thread: part (a) passes. (b) AI policy: treat every package as AI-assisted work, then read the policy as one of three cases. Requires disclosure of all AI use (in any form, including comments): the comment must say AI was used; silence fails. Conditions only (human in the loop, understand the work, comments in your own words, disclosure asked only in PRs): no disclosure line is needed in a plan comment; fail only if the comment visibly breaks a condition. Silent or permissive: passes. Bug-report template asks apply to bug reports, not plan comments: never fail on them. | required |

## Verdict rule

Accept only if every `required` check passes. Any `required` check
graded `fail` makes the verdict `reject`. `unclear` counts as `fail`: a
plan that cannot be verified from the package is not ready to build
from. This rubric has no `preferred` checks. Grade every check on every
package even after one has failed, so the output names every reason to
hold.
