# Rubric: is this pull request ready to submit?

Every check reads the artifact itself (the diff, the evidence, the
description) against the plan, the issue, and the repo's stated asks.
None of them grade length, headings, commit count, or tone. Worked
pass/fail examples for each check live in
`references/evidence-guide.md` under the family named in the check.

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| plan-fidelity | The diff's changed files and hunks, read against the plan's scope (in-scope change, not-in-scope line, files list) and its deviation notes; plus the description's own deviation/deferral statements. Evidence guide: "Plan fidelity". | Passes when every hunk in the diff is one of: the planned change, a test for it, a repo-required housekeeping entry for it (changelog, release-notes entry, i18n string, regenerated file), or a change the plan's deviation notes or the description explicitly disclose; AND every deliverable the plan commits to is in the diff, or its absence is disclosed (in the plan's deviation notes or the description). Fails if the diff adds anything else: a new option, flag, setting, or prop; a refactor, rename, or rewrite of code the fix does not need; a change to a file the plan never mentions; or behavior changes outside the planned one, with no disclosure. Also fails if a planned deliverable is missing with no disclosure. An honestly disclosed deferral passes. | required |
| description-matches-diff | Each factual claim in the PR title and description (what changed, which files or entries are included, which boxes are ticked, and fidelity claims such as "exactly as planned", "no other changes", "in full") read against the diff and commit list. Evidence guide: "Plan fidelity". | Passes when every claim the description makes about the change is true of the diff. Fails if the description claims something the diff does not contain (a docs update, a changelog entry, a test, a ticked checkbox whose work is absent), or claims fidelity or "no other changes" while the diff contains changes outside the plan. | required |
| test-evidence-decisive | The test-evidence section read against the plan's test plan and the reproduction's failing steps; plus any test or check commands the plan's test plan names. Evidence guide: "Test evidence". | Passes when the evidence re-runs every failing case the plan's test plan names (the reproduction's own trigger, not a nearby path) on the changed code AND shows its observable outcome after the fix (an output, exit code, value, or visible state), with the before state shown or quoted from the repro; AND every suite or check command the plan's test plan names appears with its outcome. Controls expected to stay unchanged may be stated in words. Fails if: the evidence is a claim without an observable ("works on my end", "checked it by hand", "the suite is green" with nothing re-run); it exercises a different path from the reproduction (a control, a simpler case, a different input); a failing case the plan names is never re-run; or a suite the plan names is never shown. | required |
| diff-reviewable | Every hunk in the diff and the commit list. Evidence guide: "Diff quality". | Passes when every hunk carries part of the change or its tests, and nothing unrelated rides along. Fails if the diff contains any of: a leftover debug statement (debug print, log, or commented-out debug line); commented-out code blocks or earlier attempts kept "for reference"; dead code (an unused function, an unused-symbol suppression added to keep scaffolding); a hunk that only reformats, re-indents, reorders imports, or reflows code the fix does not touch (lines removed and re-added unchanged); or a new TODO unrelated to the fix. Unchanged context lines inside a hunk that also carries the fix are not churn. Commit messages alone never fail this check, but a "tmp" or "misc" commit is a cue to look for debris. | required |
| standards-met | The `pull requests:` and `contribution policy` lines in the repo-facts block (live: the repo's PR template and `docs/CONTRIBUTING.md`), read against the description and diff; plus maintainer-side comments in the thread highlights (OWNER, MEMBER, COLLABORATOR, or a CONTRIBUTOR steering the design). Evidence guide: "Standards and comms". | Three parts, all must hold. (a) Template and stated asks: every section or checklist item the PR template or contributing docs ask for is present with real content (or marked n/a with a reason), and any file the asks require for this kind of change (a changelog or release-notes entry, an issue-closing line) is present. A repo with no template and no stated ask passes this part. (b) AI policy, treating every package as AI-assisted: if the policy requires disclosing AI use, the description must disclose it (tool and extent); if it sets conditions only (own words, human review, understanding), no disclosure line is needed unless the policy asks for one in PRs; if it is silent, this part passes. (c) If a maintainer-side comment asks a question or gives direction about the change, the description or plan engages it. Fails if any part fails. | required |

## Verdict rule

Accept only if every check passes. Every check is `required`: any
`fail` makes the verdict `reject`. `unclear` counts as `fail`: a PR
that cannot be verified from the package is not ready to submit.
Grade every check on every package, even after one fails, so the
output names every reason to hold. An honestly disclosed shortfall
(something the plan or description says was left out, and why) is
not a failure on any check.
