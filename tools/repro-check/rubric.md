# Rubric: is this reproduction package ready to post?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| env-recorded | The repro report's environment record (OS, tool/repo version or commit, language runtime, and any setting the issue says matters, such as driver, shell, build profile), read against the environment the issue targets (issue body, repo-facts block). | The report names the OS, the exact version or commit under test, and every environment factor the issue ties to the bug. A stranger can place the run. If the version or platform differs from the issue's, the report says so in plain words. Fail if any of these is missing, or if the environment silently differs from the issue's target. | required |
| steps-followable | The commands and actions in the repro report, read from the starting state to the trigger. | A person new to the repo can re-run the steps in order and reach the trigger. Each step is an exact command or action. Starting state (clone, install, input file, config) is given or inline: literal file contents pasted, or, when the file is not pasted, every part of its contents that the trigger depends on is named in words precisely enough to rebuild it (exact keys, sections, flags, or values that matter; a vague gesture like "my usual config" does not count). Nothing depends on a private repo, an unshared file, or unstated setup. Fail if the trigger step from the issue is missing or changed, or if any step needs a private or unstated input, or if a described (not pasted) file's trigger-relevant contents are left vague. | required |
| behavior-matches | The output excerpt, log, or screenshot in the report, read against the exact failure the issue describes (error text, exit code, crash vs graceful error, symptom). | The artifact shows the issue's own behavior, not an adjacent one. Same error class and same exit status as the issue. A config error (exit 2) is not a panic (exit 101). Garbled output with a live process is not a crash. A compile or usage error caused by an altered input is not the reported bug. The artifact comes from the version and input the issue targets, or the difference is stated. Fail if the artifact shows a different failure, only shows the tool runs, or is absent. Exception: an honest cannot-reproduce report (real attempt, real artifact, states it did not trigger the bug and names what differed) passes this check — it is judged under `honest-outcome` instead, not here. | required |
| claim-specific | The claim comment, plus the accompanying repro report when one is included in this grading pass, read against the issue and the repo-facts block. | The claim names the concrete things: the component or symptom, and the next step (file, function, or fix direction to look at); the version tested may be stated in the comment itself or in the paired report — both are read as one submission. It makes no promise the evidence cannot back, such as a guaranteed fix or a deadline. Fail if it is boilerplate that fits any issue ("assign me", "can confirm", "+1"), or if it over-promises, or if the version tested appears nowhere in the comment or report. In a claim-only draft with no report, the version must be in the comment. | required |
| honest-outcome | The report's stated result set against its own artifacts. | What the report says happened is what the artifacts show. A cannot-reproduce passes when it shows a real attempt with artifacts and names what differed and what a triggering setup may need. A "reproduced" claim passes only when the artifact shows the bug. Root-cause claims need shown evidence, else they are framed as a hypothesis. Fail if the report claims more than the artifacts show, generalizes past what was tested, or narrates a different result than the output. | required |
| repo-conventions | The claim comment and report against the repo-facts block: the bug-report template asks and the contribution policy, including any AI-use policy. | Every item the template asks for is present, given in another form, or not needed to interpret or verify this specific bug (a diagnostic dump the template asks for as routine, that this bug's evidence does not depend on). Treat course packages as AI-assisted work, then read the repo's AI policy as one of three cases: requires disclosure (comment or report must say AI was used, fail if silent), conditions such as human-voiced comments (fail only if the comment fails that condition, no disclosure line needed), or silent/permissive (nothing required, silence passes). Fail if a stated policy requirement for the matching case is not met, or if a template item that this bug's evidence depends on is missing with no equivalent given. See evidence guide Family 5 for worked examples of "depends on" vs "routine ask." | required |
| next-step-clear | The last lines of the claim comment and the report. | A reader can tell what the author will do next or what the maintainers should check. | preferred |

## Verdict rule

Accept if every `required` check passes. Reject if any `required` check fails. `unclear` on a `required` check counts as fail. `preferred` checks never change the verdict. In a claim-only draft, leave out checks that need the repro report.
